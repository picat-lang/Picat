## Planner-family programs: upstream 4.0b13 regressions (arrive with the 58ffb7a merge)
- planner_treasure.pi: native >1800s on ours (FDN=0 too), main's binary >60s, stock 3.9#12 passes; wasm leg OOMs (287s, toam).
- planner_nomystery/ricochet/solitaire.pi: native main's body NEVER runs on ours and main's 4.0b13 binaries (silent HALT0, 16ms, no output); stock 3.9#12 solves + prints answer sets; pre-merge our 4.0b8-based wasm solved them (wasm 10.7s, native 4977ms, ok=True). Instrumented probe (simplified asp/1 rules + the same 61-fact $-list in the call) runs FINE on ours, so the in-file asp/1 helper is not the interface; the breakage is in the planner import or the runtime solve path. Neither aspic nor picasp programs (plain planner with B Prolog heritage asp/1 fact helper).
- COMPLETION: the other three failed rows are broken natively TOO (silent HALT0 verified on ours for cp_ppm, sat_maxClique, sat_marriage_roman_sat; main's 4.0b13 binary empty too; stock 3.9#12 prints ANSWER/3/match facts). So ALL SEVEN failed rows are upstream 4.0b13 regressions broken on BOTH sides: planner_treasure (timeout), planner_nomystery, planner_ricochet, planner_solitaire, cp_ppm, sat_maxClique, sat_marriage_roman_sat. The compare.py native_ok was a false positive for the silent-HALT0 cases: emu/picat exits 0 on both success and the silent failure, so the harness cannot distinguish them (only the wasm wrapper's rc= line can).
- Two-stage run_asp_pi.js on planner_ricochet/cp_ppm on the merged wasm: the real solve runs 144s then dies with "Stack overflow in toam after 7 garbage collections and 6 stack expansions" (wasm32 stack limit; pre-merge these legs were ok=True).
- _bv follow-up (2026-10-31): re-verified through 4.0b13 -- coins_grid_bv on main's binary still "Undefined procedure: sat_solve_minimize_bv_sub/6" (stock 3.9#12 solves in 13ms, bv_utils.pi present). Main's lib/sat.pi contains NO bv_sub/solve_minimize definitions at all, so the predicate was DROPPED between 3.9 and 4.0, not renamed, and not restored through 4.0b13. The 19 Hakan _bv examples (hakan_examples/*_bv.pi, coins_grid_bv among them) remain broken on all 4.0 binaries; they need bv_utils.pi copied next to them to even compile.
- _bv resolution (2026-10-31, online check): the CURRENT upstream (4.0b16, built from the codeload tarball of picat-lang/Picat main) SOLVES the _bv examples -- coins_grid_bv prints "Sum: {0,1,0,1,...}" and sudoku_bv/send_more_money_bv/subset_sum2_bv/bit_patterns_bv all run without the sat_solve_minimize_bv_sub/6 existence error. So the bv objective support was fixed upstream between 4.0b13 (our merge point a137b2a, where it still fails) and 4.0b16. The predicate sat_solve_minimize_bv_sub/6 is defined in NO source file on 4.0b16 -- only as bytecode symbols in emu/picat_bc.h (the preloaded bytecode); on 4.0b16 the C-side bv-objective path finds it in the bytecode, on our a137b2a-era build it does not. Conclusion: the _bv class is fixed at 4.0b16; our tree needs another upstream merge to pick it up.
